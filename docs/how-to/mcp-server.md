# Connect an AI client to the Juddges MCP server

This guide shows how to let an MCP-capable AI client (an IDE assistant, a desktop chat app, an agent framework) search the Juddges judgment corpus. For the exact arguments and return shapes of the tools, see the [MCP tools reference](../reference/mcp-tools.md).

The server is read-only. It exposes three tools: `search_judgments`, `get_judgment` and `get_extracted_fields`.

## 1. Generate a key

1. Sign in and open **Settings**, then the **MCP access** section.
2. Click **Generate key**.
3. Copy the key from the dialog straight away. It is shown **once**: only a hash is stored, and nobody, including an administrator, can recover the plaintext later.

A key looks like `jdg_mcp_` followed by a random string. It belongs to your account and searches the corpus as you. Treat it like a password: keep it out of committed files, chat logs and screenshots.

The settings list shows only the first 16 characters of each key (the `jdg_mcp_` marker plus 8 characters of the secret), so you can tell your keys apart.

Keys created from the settings page have no name and never expire. Keys created through the API (`POST /mcp/keys`) can carry a `name` (up to 120 characters) and an `expires_at` timestamp.

## 2. Connect over HTTP (the hosted server)

The server is mounted on the backend at `/mcp`. Point your client at the backend's public address and send the key as a Bearer token:

```
URL:     https://<your-backend-host>/mcp
Header:  Authorization: Bearer jdg_mcp_<your key>
```

Many clients accept a JSON configuration along these lines. The field names differ between clients, so check yours; what matters is the URL and the `Authorization` header:

```json
{
  "mcpServers": {
    "juddges": {
      "type": "http",
      "url": "https://<your-backend-host>/mcp",
      "headers": {
        "Authorization": "Bearer jdg_mcp_<your key>"
      }
    }
  }
}
```

Use a client feature that reads the key from an environment variable or a secret store if it has one, rather than pasting the key into a file you might commit.

The transport is stateless streamable HTTP: no session is kept between requests, so any backend worker can answer any request.

## 3. Run locally over stdio (developers only)

For working on the MCP server itself you can run it over stdio instead of deploying:

```bash
export JUDDGES_MCP_KEY=jdg_mcp_<your key>
cd backend
uv run poe mcp-stdio
```

!!! warning "This is not a path for external users"
    The stdio entrypoint resolves your key by querying the database with the **service-role** credentials, so it only works for someone who already holds the backend's `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in their environment. Anyone else should use the HTTP endpoint above.

Things to know:

- `JUDDGES_MCP_KEY` holds a live credential. Export it in your shell or pass it through your MCP client's per-user configuration. Never put it in a file that is committed.
- If the key cannot be resolved the process exits with status 2 and logs "could not be resolved". That message covers a revoked key, an expired key, a key from another environment **and** missing `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`: the resolver turns every failure into "no such key", so these cases cannot be told apart. If a key you know is good is rejected, check those two variables first.
- stdout carries the protocol frames, so nothing else may write to it. Diagnostics go to stderr.

## 4. Use the tools

| Tool | What it does |
|---|---|
| `search_judgments` | Finds judgments by meaning and keyword and returns citations with short snippets. |
| `get_judgment` | Returns the text of one judgment, or one named section of it. |
| `get_extracted_fields` | Returns the structured fields already extracted for one judgment. |

A typical exchange: ask the assistant

> Find Polish Supreme Court judgments about *zachowek* from 2020 onwards, then show me the operative part of the most relevant one.

The assistant calls `search_judgments` with the query and a `date_from`, picks a hit, then calls `get_judgment` with that hit's `id` and `section: "operative_part"`.

Provenance matters when you quote a result. Only the `full_text` section of `get_judgment` is the court's own wording. `summary` is supplied by the publisher and is not verbatim. The other sections, and everything from `get_extracted_fields`, are machine-generated by the extraction pass and can be wrong. The tools label each result so an assistant can cite correctly; see the reference for how.

## 5. Revoke a key

In **Settings > MCP access**, click the bin icon next to the key and confirm. Revocation takes effect immediately in a fresh process. A backend that already resolved the key may keep accepting a revoked or expired key for up to `MCP_KEY_CACHE_TTL_SECONDS` (default 30 s, `0` disables the cache); it cannot be undone. The row is kept (marked **Revoked**) for the audit trail.

Afterwards a client using that key receives `401 Unauthorized`:

```json
{"error": "Invalid or missing MCP key"}
```

with a `WWW-Authenticate: Bearer` header. The same response is returned for a key that is expired, malformed, unknown, or missing altogether.

An MCP key can never create or revoke keys: key management accepts only a signed-in session.

## 6. Rate limits

Two limits apply. Both are configured by environment variable on the backend; see `.env.example`.

**Per key: `MCP_RATE_LIMIT`, default `120/hour`.** Every key has its own budget, in a moving window. The limit is charged **per authenticated HTTP request** to `/mcp`, not per tool call. A client's protocol traffic (`initialize`, `tools/list`) counts as well, so one tool call can cost more than one request. Over budget, the server answers `429 Too Many Requests` with a message naming the limit and a `Retry-After` header. `Retry-After` is the length of the whole window in seconds (3600 for `120/hour`), a deliberate over-estimate.

**Per IP, for rejected keys: `MCP_IP_RATE_LIMIT`, default `20/minute`.** A request carrying a `jdg_mcp_`-prefixed key that does not exist costs the server a database lookup to reject, and the per-key limit cannot see such a caller because it is charged on the key id, which only exists after a successful lookup. So each client IP also gets a budget of **rejected** keys. Valid keys never touch it, and requests with no credential, or without the `jdg_mcp_` prefix, are rejected for free and are not counted. Once an IP has spent its budget, `/mcp` answers `429` before doing any lookup, even for a valid key from that IP.

!!! warning "The per-IP limit needs `TRUSTED_PROXY=true` **and** a proxy that overwrites `X-Forwarded-For`"
    The budget is keyed on the client IP that the backend sees. Behind a reverse proxy with `TRUSTED_PROXY` unset, that address is the proxy's, the same for everybody. A limit keyed on a value shared by all callers is not a rate limit but a kill switch: twenty rejected keys from anyone would lock out every MCP user. So with `TRUSTED_PROXY` unset the per-IP budget is **not enforced** (the module logs a one-time warning), and unauthenticated lookups of bogus `jdg_mcp_` keys are unbounded. Only the per-key limit is active.

    Setting `TRUSTED_PROXY=true` makes the backend take the **leftmost** `X-Forwarded-For` entry as the client IP. That is only sound if the reverse proxy **overwrites** `X-Forwarded-For` with the real client address instead of appending to it. Measured against the gateway's Caddy v2.9.1 by sending a forged `X-Forwarded-For: 1.2.3.4` from a peer at `172.26.0.1` and reading the header back at the upstream:

    | Proxy config | Upstream sees | Leftmost client-controlled? |
    |---|---|---|
    | `reverse_proxy`, no `trusted_proxies` | `172.26.0.1` | no |
    | `reverse_proxy` + `trusted_proxies 0.0.0.0/0` | `1.2.3.4, 172.26.0.1` | **yes** |
    | `header_up X-Forwarded-For {remote_host}` | `172.26.0.1` | no |
    | `trusted_proxies` + `header_up` | `172.26.0.1` | no |

    So Caddy replaces a client-supplied value by default and only appends once the immediate peer is a configured trusted proxy. The explicit `header_up` wins either way. That is why it is set: not because the flag was spoofable on this gateway as configured, but so the guarantee stops depending on a `trusted_proxies` line, a Caddy version, or the absence of a CDN. `X-Real-IP` is a separate matter -- Caddy passes it through untouched, it **was** spoofable in that measurement, and `get_client_ip` falls back to it when `X-Forwarded-For` is absent; the gateway overwrites it too.

    Note that `TRUSTED_PROXY` also changes the key of every other IP-based rate limit in the backend, so it is a deployment-wide decision. In this deployment the blast radius is narrow, because the key only changes for requests that reach the backend with an `X-Forwarded-For` header, i.e. those arriving directly through the gateway at `juddges-api.augustyniak.ai`. Browser traffic goes through the frontend BFF, which forwards neither `X-Forwarded-For` nor `X-Real-IP`; signed-in BFF requests key on `X-RateLimit-Identity` and guest BFF requests still key on the frontend container's address, exactly as before.

!!! success "Enabled in production since 2026-10-22"
    Production runs with `TRUSTED_PROXY=true`, paired with `header_up X-Forwarded-For {remote_host}` and `header_up X-Real-IP {remote_host}` on the `juddges-api.augustyniak.ai` site in the caddy-local gateway (`data_stack`: `docker/infra/caddy-local/public-domains.caddyfile`). Caddy is the true edge there -- the DNS record is DNS-only, with no CDN in front -- so `{remote_host}` is the real client address. `X-Real-IP` is overwritten too, because `get_client_ip` falls back to it when `X-Forwarded-For` is absent and would otherwise trust a client-supplied value.

    The per-IP budget takes effect for `/mcp` with the first production image that contains the MCP server; the image deployed when the flag was set predates it.

Counters live in the storage configured by `RATE_LIMIT_STORAGE_URI`. If that storage is unreachable the limits keep being enforced, but per process in memory.
